Wirex Mobile SDK

Integration Guide

One SDK, four sealed surfaces — card Reveal, card Collect, 3-D Secure and Wallet (Apple Pay / Google Pay) top-up. This guide covers what each surface needs, where the credentials come from, how to style them, and how to run the example that exercises all four.

00The model

The SDK owns sealed UI surfaces and nothing else. A revealed PAN, a typed card number, a wallet payment token — none of them reach app code; they live inside a native view or a Wirex-hosted frame. The SDK never mints a credential, never stores one, and (for most surfaces) never decides a transaction.

Your app provides two things:

Authentication

A bearer for the signed-in user, a step-up signature when an endpoint needs a second factor, and the identity header. The SDK asks for these through a credential provider — it never creates them.

Orchestration

Your backend prices and executes the money-moving calls (top-up estimate / execute, the 3DS URL, the wallet estimate). The SDK renders the result and reports events back.

So a surface is either needs credentials (Reveal, Collect, Wallet) or no credentials (3DS — your backend already authenticated to get the URL).

02Credentials

Every credentialed surface reads from one object you implement — the WirexCredentialProvider. The SDK calls it on demand and forwards exactly one identity header (sending both X-User-Email and X-User-Wallet is a 400).

class AppCredentials : WirexCredentialProvider {
  override suspend fun accessToken(): String { /* partner auth → Wirex bearer */ }
  override suspend fun actionToken(scope: WirexActionScope): String { /* CARD_DATA / PIN */ }
  override val userEmail: String? = user.email   // return ONE of the two
  override val userWallet: String? = null        // the EOA address, if you identify by wallet
}
CredentialWhat it isHow it is minted in production
getAccessTokenBearer for the user.Your auth → Wirex BaaS. Check expiry and refresh — the SDK sends what it is given and does not retry a 401.
getActionTokenStep-up for reading card data / PIN.The user signs a confirmation message in their wallet; your backend exchanges the signature for a short-lived, one-shot action token.
userEmail / userWalletThe identity header.The signed-in user. Return exactly one.

Reveal needs credentials

Shows a cardholder their own PAN / expiry / CVV (and PIN, for plastic) in sealed native rows. The value is fetched and drawn inside a secure native view; it never reaches JS.

val reveal = WirexReveal(WirexEnvironment.resolve(name, chainId = chainId),
                         credentials, WirexLogging(WirexLogLevel.INFO, sink))
val session = reveal.createSession(cardId, cardholderName = name,
    fields = listOf(WirexRevealField.CARDHOLDER_NAME, WirexRevealField.PAN,
                    WirexRevealField.EXPIRY, WirexRevealField.CVV, WirexRevealField.PIN))
session.onSnapshot { snapshot -> /* IDLE | LOADING | READY | ERROR */ }
session.load()
// add one WirexRevealFieldView per field — a View that sizes itself
Gotcha · sizing The row pins its value area to its natural height. Give it a box shorter than its content and (from 0.3.4 on) it clips; older builds collapsed it to height 0 and drew nothing. Honour onNaturalHeight — measure, don't guess. See Appearance & sizing.
Note · simulator The revealed value is drawn in a secure capture-proof layer that the iOS Simulator renders blank. That is PCI protection working, not a bug. For simulator dev only, dangerouslyDisableScreenProtection: true draws it normally — never ship it on.

Collect needs credentials

Captures an external card's details in sealed native inputs and tokenises them at the acquirer. JS receives a token, never the PAN/CVV. Your backend then uses the token to fund a top-up.

Collect: user types card→ SDK tokenises at acquirer→ your backend: estimate→ execute → 3DS URL

The card user must be enrolled at the acquirer. Billing details (line1, zipCode, city, country) and a ≥2-char Latin label are required by the tokenizer.

3-D Secure no credentials

Presents the issuer challenge for a card payment. Your backend returns a 3DS URL from the top-up execute; the SDK renders the flow and reports the outcome. It makes no authenticated call and needs no credentials.

val threeDS = WirexThreeDS(testMode = isTestMode, logging = WirexLogging(WirexLogLevel.INFO, sink))
val session = threeDS.createSession(url)   // url from the top-up execute
session.onSnapshot { s -> /* s.state == WirexThreeDSState.SETTLED */ }
session.start()
// render WirexThreeDSView(activity) full-size
StateStatus
idle · loading · challenge · settledcompleted · pending · failed · unknown
Note pending means the payment is not settled yet — it is not an error. Reconcile the real outcome from your backend's status feed, not from the 3DS status alone.

Wallet — Apple Pay / Google Pay needs credentials real device

Embeds the Wirex-hosted checkout frame. It renders a backend-priced quote and the platform wallet button; on tap it presents the native Pay sheet. Apple Pay here runs in the web frame (no app PassKit entitlement needed).

Three inputs, all from a backend estimate + your config:

InputWhat it isFrom
quote.estimationIdA priced top-up.Your backend prices the top-up and hands the id to the app.
quote.sourceAmountThe fiat the sheet charges.The priced estimate.
providerConfigThe wallet provider block (merchant id, networks, URLs), passed verbatim.Your app config, shipped from your backend.
Note · who prices Pricing is your backend's job — it owns the user's bearer and (in token mode) also mints the checkoutToken. The SDK never prices; it only consumes an estimationId. The estimationId and the checkoutToken are two independent values — the id is not derived from the token.
val config = WirexWalletConfig(WirexWalletEnvironment.resolve(name),
    logging = WirexWalletLogging(WirexWalletLogLevel.INFO, sink), cache = cache)
val checkout = WirexWalletCheckoutView(context,
    config = config,
    quote = WirexWalletQuote(estimationId = id, sourceAmount = WirexWalletMoney("10.00", "EUR")),
    providerConfig = WirexWalletProviderConfig.fromJson(providerBlock),  // verbatim
    auth = if (tokenMode) WirexWalletCheckoutAuth(checkoutToken) else null)
checkout.onEvent = { event -> /* Ready · SheetOpen · Token (legacy) / Executed (token mode) · … */ }
Gotcha · availability To know whether to show a Pay button, start a WirexWalletAvailabilityChecker(context, config, providerConfig) and read its onChange. Give it a real provider block (with its probe_url); most emulators have no Google Pay, so it reports unavailable — the real answer there.

Legacy vs token mode. Without auth, the sheet tokenises and emits a token event — your backend executes. With a backend-minted checkoutToken, the frame executes itself and emits executing / executed / executeFailed; nothing crosses JS. The checkout arms automatically when it has a valid quote + provider block; a new quote re-arms it.

Note · device The Pay sheet cannot present on the iOS Simulator (no Secure Element). The checkout still arms; only the sheet needs a real device with a provisioned card.

03Appearance & sizing

Each surface takes an appearance object (theme mode + tokens) and a strings object — the SDK ships no copy, so the host supplies every word it draws. Colours, radii and fonts are tokens you pass; the native view renders them.

The sizing contract

A native field cannot be sized from JS. The field view measures its own content and reports it through onNaturalHeight; apply that height to the row rather than hardcoding one. If a host ignores it and pins a box too small, the row clips its value (0.3.4+) instead of vanishing — but the right pattern is to measure.

Tip Full token lists live in the SDK's README (“Customization & sizing”). The same contract holds on iOS, Android and Flutter.

04Running the example

The SDK ships a runnable example that exercises all four surfaces against your own data — nothing is hard-coded. Enter your integration parameters and credentials (bearer, identity, card id, chain, provider config) in its Config tab; every screen reads them live, so one build covers every surface with no rebuild. The field set is the same across the iOS, Android and Flutter examples.

05Backend calls

Your backend performs the money-moving work with the credentials Wirex issues for your integration — pricing a top-up, executing it, minting a checkout token (token mode), and serving the wallet provider config. The SDK consumes their results; it makes none of these calls itself.

Authenticated calls carry Authorization: Bearer, X-Chain-Id and one identity header (X-User-Email or X-User-Wallet, never both). For the exact paths, request and response shapes, see the Wirex BaaS API reference Wirex provides with your integration.
